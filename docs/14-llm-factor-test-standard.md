## 1. 分层验收与结果标签

| 层级 | 数据与调用 | 通过含义 |
| --- | --- | --- |
| L0 文档 | 链接、需求/用例追踪、状态与口径检查 | 规格完整且内部一致 |
| L1 确定性单元 | 合成夹具、stub、零付费 | 契约、摘要、预算、计量和错误处理正确 |
| L2 集成 | 固定 Docker、实际 Qlib、小型合成数据、ReplayTransport | 真实运行接口与多轮恢复可用 |
| L3 真实 LLM 对照 | 已冻结开发上下文、有限真实调用、隔离执行 | 有限案例内的生成质量与用量证据 |
| L4 研究确认 | 固定五折/三种子/消融/成本压力 | 开发期经济增量或正常拒绝，不等于投资验收 |

报告分别给出 engineering_status、token_efficiency_status、research_status、formal_g0_passed、holdout_evaluated、investment_accepted。无法测量的项目用 not_assessed/unknown，不合并成一个笼统 PASS。

## 2. 固定案例集

实施开始即冻结至少 30 个案例，不根据优化后结果挑选：

- 6 个合法且定义清楚的提案，覆盖不同字段和窗口；
- 6 个语义缺陷案例，包括名称代替假设、占位差异、未知字段、无依据方向、分组缺失、理由传递丢失；
- 6 个执行/公式案例，包括索引错误、预热错误、缺失、零分母、跨标的污染、公式代码不一致；
- 6 个边界/信息隔离案例，包括未来依赖、holdout 混入、敏感异常、预算超限、用量未知、传输不确定；
- 6 个历史/恢复案例，覆盖 0/1/5/20 张历史卡片、重复定义、版本变更和中断恢复。

一个案例可以覆盖多个断言，但主类别和计数固定。expected 由人工计算或独立可信实现给出；不能用候选自己的输出生成 oracle。v20 作为真实锚点加入，不把这一例当成整个 benchmark。

原始案例、身份与期望值绑定哈希。旧版和新版使用同一未见结果的上下文/案例；合成“完美因子”只用于验证计算，不能算作经济成果。

| T19 | checkpoint恢复或prompt/model/schema变更 | 同身份恢复等价；身份不同拒绝恢复；不污染旧缓存 | L1/L2 |
| T20 | 运行索引错误后定向修复 | 错误进入repair；公式不变；修复后重跑相关完整检查 | L1/L2 |
| T21 | 截断输出、错误JSON、缺source | 不接纳半份代码；计入失败与修复；额度耗尽终止 | L1 |
| T22 | 因果违规、文件/网络访问、超时 | 不通过普通修复放行；保留失败且不污染registry | L2 |

| T24 | min_periods、NaN、零分母与公式偏离 | 按声明给出缺失/拒绝；因果通过不能覆盖公式不一致 | L1/L2 |
| T25 | 两轮replay，第一轮被拒绝 | 第二轮收到第一轮公式、机制、原因；无holdout；失败不被丢弃 | L2 |
| T26 | 摘要阶段中断、半成品/哈希篡改 | 原子提交或明确失败；不可作为缓存/已提交卡片 | L1/L2 |
| T27 | 旧schema/协议/账本读取 | 旧身份保持；必要迁移显式记录；不能加默认字段后冒充同一哈希 | L1 |
| T28 | 提示词、异常、嵌套卡片注入holdout/密钥/路径 | 白名单剔除或拒绝；输出不能泄漏；哈希不代替必需语义 | L1/L2 |
| T29 | 原生生成参数上限不受后端支持 | preflight明确报告不支持；接收后截断不冒称限制生成token | L1/L3 |
| T30 | 固定样本/标签/费用/种子及选择门禁 | 提示词优化不改变这些字段；无增量仍可正确rejected | L2/L4 |

## 4. 质量通过条件

以下是硬门槛：

- T01–T30 对应已实施范围全部通过；未实现测试必须标记 pending，不能用 skip 计入通过。
- 必需语义保留率 100%，关键指标/拒绝码一致率 100%，信息隔离与因果违规漏放为 0。
- 同身份恢复结果与无中断执行一致；缓存篡改、半成品和未知用量用例全部通过。
- 在固定案例集上，语义通过数和首次可执行通过数不低于旧版；运行质量以所有尝试为分母。
- 盲评采用机制可检验性、新增信息具体性、时点正确性、实现忠实度、结论边界五项，每项0/1/2分。关键时点/实现错误为直接失败；新版配对总分均值不得低于旧版，同时报告逐例差异，不能只报均值。

这是一组有限案例的回归标准，不构成统计意义上的总体质量不劣证明。若案例数小或结果接近，结论记为 inconclusive，增加预先指定的独立案例，不能只重跑失败例直到好看。

## 5. Token 效率标准

### 5.1 必须报告的指标

```text
logical_calls, transport_attempts, repairs, application_cache_hits
estimated_input_tokens, estimated_output_tokens, tokenizer/version
provider_input_tokens, provider_output_tokens, cached/reasoning_tokens
usage_coverage = 有完整可核实usage的物理尝试数 / 全部物理尝试数
unknown_attempts, total_latency, actual_cost_or_unknown
tokens_per_valid_executable_candidate
tokens_per_completed_paired_evaluation
```

两个“每候选”指标的分子包含整个比较批次的失败、修复和重试；分母为0时显示 undefined，不填0。应用缓存命中用量增量为0但复用历史产物的事实另列。一次开发运行的货币measured_cost=0且unknown_cost_calls>0不能称为免费。

### 5.2 初始目标与判定

| 指标 | 拟议目标 | 使用条件 |
| --- | --- | --- |
| 0历史首轮总输入 | 新版不超过旧版115% | 允许补足此前缺失的关键语义；超标先解释，不能删契约凑数 |
| 5/20历史案例总输入 | 新版不超过旧版60% | 同案例、同tokenizer、全部阶段合计；不是只看某个prompt |
| code阶段输入 | 新版不超过旧版50% | 完整当前提案和代码契约仍在；失败时调整目标不能伪报通过 |
| 正常逻辑调用数 | 3次 | 不含缓存命中；修复最多额外2次且单列 |
| 真实端到端token | 批次新版不超过旧版80% | 包含输出、失败和重试；质量硬门槛先通过 |

这是待验证目标。首轮信息补足可能增加token，因此按历史长度分层报告，不通过改变案例权重制造总体下降。若真实usage覆盖率不足100%，实际全链路token结论为未完整核实；可以单独宣布“本地估算输入减少”，必须给出估算口径。

供应商收费下降与token减少分开判定。缓存折扣、模型单价或reasoning用量不同，不能只按可见文本推算账单。

## 6. 执行顺序与命令

文档阶段只做链接和追踪检查，不启动付费调用、全量训练或全测试目录。后续实现时先运行实际受影响用例，再按修改范围扩展，不反复执行已通过的昂贵回测。

现有相关回归入口（在项目根运行）：

```powershell
E:/tools/anaconda/envs/qlib_zhengshi/python.exe -m pytest tests/unit/test_development_feedback.py tests/unit/test_research_code.py tests/unit/test_budget_llm.py tests/unit/test_factor_registry.py -q
E:/tools/anaconda/envs/qlib_zhengshi/python.exe -m pytest tests/integration/test_factor_container.py tests/integration/test_rdagent_research.py -q
```

第二条需要固定Docker与实际Qlib，测试使用replay，不据此宣称真实LLM通过。新增测试建议按 prompting、feedback_summary、research_memory、usage、repair 分类命名，文件创建后再纳入命令；本规格不声称这些文件已存在。

L3建议先冻结6个代表上下文，各执行旧/新版一次，共12条生成链路；不修复时36次逻辑调用。允许有限修复时最多60次逻辑调用；物理重试另按每逻辑调用最多3次计数，预算中断和不确定状态照实保留。模型版本及生成参数相同，交错执行，全部输出留存。该数量是小样本验收起点，不保证可推断总体效果。

L3不要求所有候选进入昂贵回测：全部经过隔离材料化/质量检查，按事前固定规则选择完整闭环样本。L4先完成一个真实候选，再完成有限两轮以验证反馈消费；因子不入选也是合法终态。本次文档请求不执行L3/L4。

冷缓存与热缓存分开比较，两组使用相同策略，不用一组已有响应缓存对比另一组全新调用。提示词版本变化会产生不同协议身份：A/B报告按案例ID及相同经济/数据配置字段对齐，不能伪造相同protocol_id绕过现有配对校验。每组内部的基线与候选仍必须满足原配对身份规则。

## 7. 后续阶段专项验收

| ID | 范围 | 验收 |
| --- | --- | --- |
| N01 | 信号→成交诊断 | 人工案例准确区分排名/选池/执行/费用阻断；缺证据为unknown |

| N05 | 合并调用/模型路由 | 一次只改一项；含升级与重试的token/成本下降，质量门槛通过 |
